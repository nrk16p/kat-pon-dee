# แผน PoC — โหมดนับด้วยมือ + MacBook เป็นเซิร์ฟเวอร์

เขียน 2026-07-30 · ต่อจาก `manual-flow-counting.md`

---

## 1. ใช้ MacBook เป็นเซิร์ฟเวอร์ไหม — ควร และมันทำได้มากกว่าที่คิด

### เหตุผลที่ควร

**1. มันหยุดเลือดที่ไหลอยู่ตอนนี้**
Render ตอบ `persisting: false` — `/data` ไม่ได้ mount ทุกภาพและทุกทะเบียนชาวสวน
**หายไปเงียบ ๆ ตั้งแต่วันแรก** MacBook มีดิสก์จริง แก้ได้วันนี้

**2. เร็วกว่ามาก**
Render ใช้ 16–18 วินาทีต่อภาพที่ 5 px/มม. เครื่องนี้ทำ segmentation ใน 187 มส.
ต่างกันระดับ 50–100 เท่า — และความเร็วนี้คือสิ่งที่ทำให้ข้อ 3 เป็นไปได้

**3. มันทำให้ PoC ไม่ต้องรอการพอร์ต WASM 3–4 สัปดาห์** ← สำคัญที่สุด
ดูข้อ 2

**4. ย้ายไป DigitalOcean ทีหลังแทบไม่ต้องแก้อะไร**
storage เป็นไฟล์ล้วน (`data/captures/` + `data/growers.jsonl`) ไม่มี DB engine
ย้ายคือ `rsync` ไม่ต้อง dump/restore ไม่ต้อง migrate schema
**นี่เป็นข้อดีของการออกแบบเดิมที่ควรรักษาไว้ตลอด PoC — อย่าเพิ่งใส่ Postgres**

## 2. ทางลัดที่ทำให้ PoC เสร็จใน ~2 สัปดาห์แทน 6

แผนเดิมบอกว่าต้องพอร์ต pipeline ทั้งเส้นไป WASM ก่อน (3–4 สัปดาห์)
**สำหรับ PoC ไม่ต้อง** เพราะโครงสร้างโหมดมือไม่ได้ต้องการการวัดแบบต่อเนื่อง

```
สิ่งที่ต้องทำต่อเนื่อง 30 fps  →  ตรวจว่านิ่งหรือยัง  →  JS ล้วน ไม่ต้องใช้ CV
สิ่งที่ทำครั้งเดียวตอนนิ่ง     →  วัดขนาดทุกลูก      →  ส่งไปให้ Mac ทำ
```

**วัดแค่ครั้งเดียวต่อการวางหนึ่งรอบ ไม่ใช่ทุกเฟรม** ฉะนั้นส่งภาพไปเซิร์ฟเวอร์ได้สบาย

```
┌── มือถือ ────────────────────┐        ┌── MacBook ──────────┐
│  กล้อง 30 fps                 │        │                     │
│    │                         │        │                     │
│    ▼                         │        │                     │
│  frame-diff 64×64  (JS ~1มส.) │        │                     │
│    │                         │        │                     │
│    │ นิ่งครบ 300 มส.           │        │                     │
│    ▼                         │        │                     │
│  ส่ง 1 เฟรม ─────────────────────────►│  หามาร์กเกอร์         │
│                              │        │  warp + แยกผลไม้     │
│  วาดโซน + วงสี  ◄─────────────────────│  188 มส.             │
│  tracker + นับ    (JS ล้วน)   │        │  → homography +      │
│                              │        │    ผลไม้ทุกลูก        │
└──────────────────────────────┘        └─────────────────────┘
```

**ไม่ต้องใช้ opencv.js เลยใน PoC** เพราะ:
- ตรวจนิ่ง = frame-diff ธรรมดา ไม่ต้องใช้ CV
- homography ได้จากเซิร์ฟเวอร์ทุกครั้งที่วัด
- **มือถืออยู่บนขาตั้ง ไม่ขยับ** → homography เดิมยังใช้ได้ระหว่างรอบ
- tracker กับ state machine เป็นตรรกะล้วน ไม่แตะพิกเซล

⚠️ ข้อแลกเปลี่ยน: ถ้ายกมือถือถือเอง หรือชนขาตั้ง โซนจะเลื่อนจนกว่าจะวัดรอบถัดไป
**รับได้สำหรับ PoC บนขาตั้ง** ถ้าจะถือมือต้องมี opencv.js (ระยะ 1)

## 3. เรื่องเครือข่ายที่ต้องรู้ก่อน ไม่งั้นเสียเวลาหนึ่งวัน

### ⚠️ ห้ามยิงตรงไปที่ LAN IP

ความคิดแรกคือให้มือถือยิงไปที่ `http://192.168.1.x:8000` บน WiFi เดียวกัน เร็วที่สุด
**แต่ทำไม่ได้** — หน้าเว็บเสิร์ฟจาก Vercel ผ่าน HTTPS การยิง HTTP ออกไปคือ
mixed content เบราว์เซอร์บล็อกทิ้ง

### ทางที่ใช้: Cloudflare named tunnel

```
มือถือ ──HTTPS──► Cloudflare ──tunnel──► MacBook:8000
```

**named tunnel ไม่ใช่ quick tunnel** — quick tunnel เปลี่ยน URL ทุกครั้งที่รีสตาร์ต
ต้องไปแก้ env ใหม่ทุกรอบ named tunnel ได้ชื่อโดเมนคงที่

งบเวลาต่อการวางหนึ่งรอบ:

| | เวลา |
|---|---|
| ส่งภาพ 720p (~150KB) ผ่าน tunnel | ~150–300 มส. |
| ประมวลผลบน Mac | ~190 มส. |
| ส่งผลกลับ (JSON เล็ก) | ~100 มส. |
| **รวม** | **~0.5 วินาที** |

ครึ่งวินาทีต่อการวางหนึ่งกำมือ (15–20 ลูก) **รับได้สบาย**

ถ้าทดสอบแล้วรู้สึกช้า ค่อยทำ LAN โดยตรงด้วย `mkcert` + ติดตั้ง CA บนมือถือทดสอบ
— แต่**อย่าทำก่อน** จนกว่าจะพิสูจน์ว่าจำเป็น

### สิ่งที่ต้องตั้งบน Mac

| | ทำไม |
|---|---|
| `caffeinate -s` ตอนรัน | ปิดฝา/หลับ = เซิร์ฟเวอร์ตาย |
| **โทเคนยืนยันตัวตน** | tunnel เปิดสู่อินเทอร์เน็ต ใครมี URL ก็อัปโหลดได้ |
| **สำรอง `data/`** | MacBook เครื่องเดียว = จุดตายจุดเดียว และชุดข้อมูลนี้คือของที่มีค่าที่สุดในโปรเจกต์ |
| จำกัดขนาดอัปโหลด | กันคนอื่นถมดิสก์ |

> ชุดภาพลำไยจริง 300–500 ใบ คือสิ่งเดียวที่ปลดล็อกระยะ 3 ได้
> **ถ้า MacBook พังแล้วไม่มีสำรอง คือเสียเวลาทั้งฤดูกาล**

## 4. งานที่ต้องทำ

### ขั้น 0 — หยุดข้อมูลหาย · ครึ่งวัน

- ตั้ง named tunnel ชี้มาที่ Mac
- ชี้ `VITE_API_URL` ไปที่ tunnel (ไม่ใช่ `VITE_API_BASE` — โค้ดอ่านชื่อนี้)
- ยืนยัน `/api/health` ตอบ `persisting: true`
- ตั้งสำรอง `data/` อัตโนมัติ

**ทำได้ทันที ไม่ต้องรอฟีเจอร์** และเป็นงานที่คุ้มที่สุดในเอกสารนี้

### ขั้น 1 — เซิร์ฟเวอร์: session + นับ · 2 วัน

```
POST /api/session          เปิดรอบนับ → sessionId
POST /api/session/{id}/frame   ส่ง 1 เฟรม → homography + ผลไม้ทุกลูก + pixel→mm
POST /api/session/{id}/count   ยืนยันยอดนับ (มาจากตรรกะฝั่งมือถือ)
GET  /api/session/{id}     สรุปรอบ
```

- `/frame` ใช้ pipeline เดิมทั้งดุ้น แต่คืน **ตำแหน่งเป็น มม. บนแผ่น** ด้วย
  (tracker ต้องใช้พิกัดแผ่น ไม่ใช่พิกัดภาพ ไม่งั้นมือถือขยับนิดเดียว ID หลุดหมด)
- เก็บทุกเฟรมลง `data/captures/` เหมือนเดิม ← นี่คือชุดข้อมูลระยะ 3
- session เก็บเป็น JSONL ตามแบบเดิม **ไม่ใส่ DB**

### ขั้น 2 — มือถือ: ตรวจนิ่ง + วัดหนึ่งช็อต · 2 วัน

```
src/lib/live/stillness.ts    frame-diff 64×64 บน canvas เล็ก
src/lib/live/session.ts      คุยกับ API รอบนับ
```

- เปิดกล้องด้วย `getUserMedia` ต่อเนื่อง
- ตรวจนิ่ง → ยิงหนึ่งเฟรม → ได้ผลกลับ

### ขั้น 3 — โซนเกาะแผ่น · 2 วัน

```
src/lib/cv/zones.ts             นิยามโซนเป็น มม. + แปลงผ่าน homography
src/components/ZoneOverlay.tsx  วาดโซน 4 ส่วน + สถานะแต่ละโซน
```

- โซนนิยามเป็น **มิลลิเมตรบนแผ่น** (เข้า 60 · วัด 230×290 · ออก 60)
- **ล็อกให้ใช้ได้เฉพาะแผ่น 500 มม.** — A3/A4 พื้นที่ไม่พอ ต้องบล็อกไม่ให้เลือก

### ขั้น 4 — tracker + state machine · 3 วัน

```
src/lib/live/tracker.ts
```

- จับคู่ ID ด้วย centroid ในหน่วย มม. ระยะ < 10 มม.
- เก็บ ID ที่หายไว้ 3 วินาที (มือบัง)
- `NEW → MEASURED → COUNTED`
- **ต้องผ่าน MEASURED ก่อนถึงนับได้** — ปัดเร็วเกินไม่นับ แล้วเตือน

### ขั้น 5 — หน้าจอนับ · 2 วัน

```
src/features/CountPage.tsx
```

- แถบสะสม: จำนวน + สัดส่วนเกรด
- **เสียง + กะพริบตอนนับ** ขาดไม่ได้
- **ปุ่มแก้ไข (−1 / ยกเลิกรอบ)** ขาดไม่ได้
- เตือน: ติดกัน · ออกผิดทาง · ยังไม่นิ่ง

### ขั้น 6 — ทดสอบกับลำไยจริง · 2 วัน

- นับด้วยมือ 200 ลูก เทียบกับที่แอปนับ → **นับขาด/เกินกี่ลูก**
- วัดด้วยเวอร์เนีย 50 ลูก เทียบกับที่แอปวัด → **bias จริงเท่าไร**

**นี่คือขั้นที่สำคัญที่สุด** ขั้น 1–5 คือการสร้างเครื่องมือ ขั้น 6 คือการรู้ว่ามันจริงไหม

## 6. เส้นทางไป DigitalOcean

ไม่ต้องเขียนใหม่ เพราะ storage เป็นไฟล์ล้วน

```
Droplet $12/เดือน (2 vCPU · 2GB) + Volume 50GB
   ├── โค้ดชุดเดิม start.sh ชุดเดิม
   ├── rsync data/ จาก Mac ขึ้นไป
   └── ชี้ VITE_API_URL ใหม่
```

**สิ่งที่ต้องรักษาไว้ระหว่าง PoC เพื่อให้ย้ายง่าย:**
- ทุก path มาจาก env (`CAPTURE_DIR`, `GROWERS_FILE`) — ทำอยู่แล้ว **อย่า hardcode**
- ไม่ใส่อะไรที่ผูกกับ macOS
- ไม่ใส่ DB engine จนกว่า JSONL จะเอาไม่อยู่จริง

เทียบกับ Render: DigitalOcean 2 vCPU เร็วกว่า Render Starter หลายเท่าที่ราคาใกล้กัน
และ **มี volume จริง** ซึ่งเป็นปัญหาที่ทำให้ข้อมูลหายอยู่ตอนนี้
