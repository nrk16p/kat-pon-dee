# แผนลงมือทำ Real-time

ต่อจาก `realtime-plan.md` — เอกสารนี้บอกว่าจะเขียนอะไร ที่ไฟล์ไหน ลำดับไหน
และจุดไหนคือจุดตัดสินใจว่าจะไปต่อหรือถอย

---

## ระยะ 0 — Spike พิสูจน์ความเป็นไปได้ · 2–3 วัน

**ต้องทำก่อนอย่างอื่นทั้งหมด** ทุกตัวเลขที่ผมมีวัดบน Mac ผ่าน Python
ยังไม่เคยวัด WASM บนมือถือจริงสักครั้ง ถ้าช้ากว่าที่คาด 20 เท่า แผนทั้งหมดพัง
ควรรู้ตอนนี้ ไม่ใช่ตอนสัปดาห์ที่สาม

### ทำอะไร

1. เพิ่ม `opencv.js` เข้าโปรเจกต์ (โหลดแบบ lazy ตอนเปิดกล้องเท่านั้น)
2. **ยืนยันว่ามี ArUco จริง** — `cv.aruco_ArucoDetector` และ
   `cv.getPredefinedDictionary(cv.DICT_4X4_50)`
   ArUco ย้ายจาก contrib เข้า `objdetect` ตั้งแต่ OpenCV 4.7 แต่ build ของ
   opencv.js อาจตัดโมดูลออก **ถ้าไม่มี ต้อง build เองซึ่งเพิ่มงาน 3–5 วัน**
3. หน้าทดลอง `/spike` (ไม่ใส่ใน nav): เปิดกล้อง → หามาร์กเกอร์ทุกเฟรม →
   แสดง fps · เจอกี่มุม · เวลาต่อเฟรม
4. ทดสอบบน **Android จริง + iPhone จริง** ไม่ใช่ desktop

### ตัวเลขที่ต้องบันทึก

| | เกณฑ์ผ่าน |
|---|---|
| fps การหามาร์กเกอร์ ที่ 720p | **≥ 15 fps** |
| ความเสถียร 4/4 ขณะถือมือ | ≥ 90% ของเฟรม |
| ขนาดที่โหลดเพิ่ม | ≤ 10 MB |
| เวลาโหลดครั้งแรก บน 4G | ≤ 5 วินาที |

### จุดตัดสินใจ

- **≥ 15 fps** → ไประยะ 1
- **8–15 fps** → ไปต่อได้ แต่ลดเหลือ 540p และตรวจทุก 2 เฟรม
- **< 8 fps** → หยุด กลับไปทำโหมดถ่ายนิ่งให้ดีแทน

## ระยะ 1 — กรอบสดขณะเล็ง · ~1 สัปดาห์

ยังไม่วัดขนาด แค่บอกว่าถ่ายแล้วจะใช้ได้ไหม **มีคุณค่าในตัวเองแม้ระยะ 2 ไม่ได้ทำ**

### ไฟล์ที่เพิ่ม

```
src/lib/cv/loader.ts        โหลด opencv.js แบบ lazy + cache
src/lib/cv/markers.ts       หามาร์กเกอร์ → 4 มุม + homography
src/components/LiveGuide.tsx  วาดกรอบแผ่นจริงทับภาพสด
```

### ไฟล์ที่แก้

```
src/features/CapturePage.tsx   ใช้ LiveGuide แทน MatGuide
                               ล็อกปุ่มถ่ายจนกว่าจะครบ 4 มุม
```

### สิ่งที่แสดงสด

- เจอมาร์กเกอร์กี่มุม (2/4 · 4/4) พร้อมไฮไลต์มุมที่ยังไม่เจอ
- **กรอบวัดวาดตามตำแหน่งจริงของแผ่น** ไม่ใช่กรอบลอยกลางจอแบบตอนนี้
- ความคมพอไหม (ใช้ตัววัดจากขอบมาร์กเกอร์ที่มีอยู่แล้วใน `markers.py`)
- ไกล/ใกล้เกินไป จาก solvePnP

> `MatGuide.tsx` ปัจจุบันวาดกรอบไว้กลางจอเฉย ๆ ไม่เกี่ยวกับแผ่นจริงเลย
> ระยะนี้ทำให้มันเป็นของจริง

## ระยะ 2 — วัดสด · 3–5 สัปดาห์

### 2.1 พอร์ต pipeline ไป TypeScript

**Python คือ spec** พอร์ตให้ตรง แล้วพิสูจน์ว่าตรงจริง

```
src/lib/cv/rectify.ts     warp ตาม homography ที่ 2.5 px/มม.
src/lib/cv/mask.ts        แยกผลไม้จากแผ่น (พอร์ตจาก _fruit_mask)
src/lib/cv/watershed.ts   local maxima + watershed (พอร์ตจาก _watershed)
src/lib/cv/measure.ts     contour → ขนาด + occlusion + hue filter
src/lib/cv/optics.ts      ชดเชยความสูง (พอร์ตจาก optics.py)
```

**ต้องมีการตรวจสอบข้าม** — สร้างภาพทดสอบจาก `tools/synthetic.py` เก็บเป็น fixture
แล้วเขียนเทสต์ที่ยืนยันว่า TS กับ Python ให้ผลตรงกันภายใน 0.05 มม.
ถ้าไม่ทำ จะมีสองระบบที่วัดไม่เท่ากันโดยไม่มีใครรู้

### 2.2 Worker + แคช

```
src/workers/segment.worker.ts   รัน pipeline นอก main thread
src/lib/cv/liveEngine.ts        จัดการรอบการทำงาน
```

ตรรกะ:

```
ทุกเฟรม     หามาร์กเกอร์ (6 ms) → homography ใหม่
            → ฉายผลที่แคชไว้ลงตำแหน่งใหม่ → วาด
ทุก ~1 วิ    ถ้าฉากเปลี่ยน ส่งเฟรมเข้า worker → แยกผลไม้ → อัปเดตแคช
```

ตรวจว่าฉากเปลี่ยนด้วยการเทียบเฟรมแบบหยาบ (ย่อเป็น 64×64 แล้วหาผลต่าง)
เพื่อไม่คำนวณซ้ำตอนที่ไม่มีอะไรขยับ

### 2.3 หน้าจอ

```
src/features/LiveGradePage.tsx
```

- วงกลมสีตามเกรดเกาะติดผลไม้
- ตัวนับสดด้านบน: จำนวน · เฉลี่ย · สัดส่วนเกรด
- ลูกที่ใกล้เส้นแบ่ง ≤ 0.5 มม. → **แสดงเป็น "ก้ำกึ่ง" ไม่เดา**
- ปุ่ม "ถ่ายเพื่อบันทึก" → เข้าเส้นทางเดิม วัดละเอียด เก็บภาพ

### 2.4 แยกให้ชัดว่าอันไหนคำแนะนำ อันไหนบันทึก

| | สด | ถ่ายนิ่ง |
|---|---|---|
| ความแม่น | ±0.5 มม. | ±0.05 มม. |
| ใช้ทำอะไร | ช่วยคัด | หลักฐานส่งผู้รับซื้อ |
| เก็บภาพ | ไม่ | เก็บ |

**หน้าจอต้องบอกความต่างนี้ให้ชัด** ไม่งั้นชาวสวนจะเอาเลขจากโหมดสดไปต่อรองราคา
แล้วผู้รับซื้อวัดได้ไม่ตรง

## ความเสี่ยงที่ต้องจับตา

| ความเสี่ยง | ถ้าเกิดขึ้น |
|---|---|
| opencv.js ไม่มี ArUco | build เอง +3–5 วัน |
| WASM ช้ากว่าคาดมาก | ลดเป็น 540p / ตรวจทุก 2 เฟรม / ถอยไปโหมดถ่ายนิ่ง |
| bundle ใหญ่เกินไป | โหลดเฉพาะตอนเปิดกล้อง (วางแผนไว้แล้ว) |
| iOS จำกัดกล้องใน PWA | ทดสอบใน LIFF ด้วยตั้งแต่ spike |
| TS กับ Python วัดไม่ตรง | เทสต์ข้ามจะจับได้ก่อนถึงมือผู้ใช้ |

## ⚠️ เงื่อนไขที่ควรทำก่อน

**ยังไม่เคยทดสอบกับลำไยจริงสักครั้ง**

real-time จะทำให้ระบบดูฉลาดขึ้นมากโดยที่ความแม่นเท่าเดิม ถ้าตัวเลขยังไม่เคย
พิสูจน์กับเวอร์เนีย การทำ real-time คือการทำให้คนเชื่อสิ่งที่ยังไม่รู้ว่าถูกไหม
เร็วขึ้น 30 ครั้งต่อวินาที

**ทำ spike ระยะ 0 คู่ขนานไปได้เลย** เพราะไม่แตะตรรกะการวัด แต่ก่อนปล่อยระยะ 2
ให้ชาวสวนใช้ ควรมีผลเทียบเวอร์เนียแล้ว
